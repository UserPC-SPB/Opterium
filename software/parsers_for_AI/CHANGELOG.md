# Журнал изменений any_txt_parser

Версии идут от новой к старой. Пометка **[контракт]** означает изменение, после которого
потребитель вывода или существующий шаблон может увидеть другой результат: другой код
выхода, другой статус или текст предупреждения, другой формат по сниффингу, другой вид
данных или `## Effective Template`. Подробности поведения — в `FULL_GUIDE.md`, краткая
справка — в `HELP.md`. Номера разделов в скобках (§N) в записях по 1.5.0 включительно
относятся к удалённому русскому руководству `FULL_GUIDE_RU.md` (файл удалён из репозитория).

«Раньше» во всех пунктах 1.0.4 — это выпущенный exe 1.0.3 (dist от 2026-10-14).

## Не выпущено

Исправления репозитория по внешней проверке 1.5.0. Поведение программы не менялось.

- `FULL_GUIDE_RU.md` удалён: полное руководство только английское — `FULL_GUIDE.md`.
- `tests/fuzz.rs` не собирался на rustc 1.95.0 (24 ошибки E0277/E0308): `Rng::pick`
  возвращал `&T`, и старый компилятор выводил `T = str` из ожидаемого `&str` в вызовах вида
  `push_str(rng.pick(&["…"]))`. Теперь `pick` возвращает элемент по значению; случайная
  последовательность и сами случаи прежние.
- Компилятор закреплён: `rust-toolchain.toml` — rustc 1.97.1 (им собран выпущенный 1.5.0;
  rustup поставит его при первой сборке).
- Сборка воспроизводима: линкер получает `/Brepro` (`.cargo/config.toml`) и не пишет время
  сборки в заголовки PE; `scripts/release.ps1` убирает из exe пути `<CARGO_HOME>\registry\src`
  сборочной машины (`--remap-path-prefix`). Одинаковые исходники, rustc и набор MSVC дают
  побайтно одинаковый exe.
- Один конец строки: `.gitattributes` — `* text=auto eol=lf` (`.bat` — CRLF, `tests/snapshots/**`
  без преобразований), поэтому рабочая копия, `git archive` и архив исходников везде с LF,
  какой бы ни была `core.autocrlf`.
- BOM в начале `crates/navguard/src/watch.rs` удалён.
- `examples/errors.yml` и `examples/example.log` упомянуты в `README.md` и проверяются тестом
  `readme_example_finds_the_error_with_its_context` (`tests/golden.rs`).
- `README.md`: размер exe «~6.4 MB» (было «~6.5 MB»); ссылки на русское руководство в README,
  `my_memory.md` и комментариях тестов заменены.

## 1.5.0 — 2026-10-19

Три неудобства для работы с кодом, найденные при оценке 1.4.0: шумный `todos`, `find` без
точного совпадения, `extract` без номеров строк. «Раньше» — выпущенный 1.4.0. Тесты —
`tests/one_exe.rs` (`extract_lines_exact_find_and_strict_todos`, через настоящий exe и
MCP), `tests/api.rs` (`text_rules_report_source_lines`,
`stable_deduplicate_keeps_the_lines_of_the_kept_items`), модульные тесты navguard `api` и
адаптера `text`.

### `extract`: номера строк

- **[контракт]** Элементы текстовых правил (`contains`, `starts_with`, `ends_with`, `regex`,
  `line`) в текстовом выводе начинаются с номера строки источника в стиле grep:
  `- L12: текст` — строка совпадения, `L11- ` — строки контекста (`--context`) и остальные
  строки диапазона `line:A-B`; нумеруется каждая строка элемента. Если преобразование
  изменило число строк элемента (`truncate_lines`, `--max-item-chars`, `trim`, …), помечена
  только первая строка — исходным диапазоном: `- L41-L43: …`. Раньше номеров не было, и чтобы
  править найденное, агенту приходилось искать строку заново. Кто разбирает текстовый вывод
  программой, должен снимать префикс (или брать `--json`).
- **[контракт]** JSON (`--json`, MCP `output: "json"`): у результата текстового правила новые
  поля `lines` — номер строки совпадения для каждого элемента, параллельно `items` (у
  `line:A-B` — A) — и `spans` — `[первая, последняя]` строка каждого элемента, если хоть один
  элемент занимает несколько строк (контекст, диапазон). Прежние поля не изменились; у других
  селекторов, у пустых результатов и после `join` новых полей нет. Номера идут за элементами
  через `unique`, `sort`, `limit_items`, `max_items`, `stable_deduplicate` и обрезку
  `max_output_chars`.
- Режим отчёта (`-i -t -o`, Markdown-документ) не изменился: номеров строк в нём нет.

### `find --exact`

- `find PATTERN --exact` и аргумент `exact: true` инструмента MCP `find_symbol`: только
  символы, чьё имя равно шаблону (у C++ `Foo::bar` — также `bar`); подпись и путь не
  учитываются, регистр — как без ключа (без учёта, если нет `--case-sensitive`). Раньше было
  только вхождение подстроки в имя, подпись или путь: на исходниках serde_json
  `find from_str` давал 8 символов, среди них `from_string`, `from_string_unchecked` и
  `test_deserialize_from_stream`; с `--exact` — 5 настоящих `from_str`. Заголовок текста:
  `find 'cart' (exact name): 2 symbol(s)`. API: `FindOptions::exact`.

### `todos`: маркеры целым словом

- **[контракт]** `todos` (CLI, MCP, `nav --todos`) ищет маркеры TODO, FIXME, HACK и XXX целым
  словом (рядом нет буквы, цифры или `_`): заглавными или в любом регистре, если сразу после
  идёт `:`, `(`, `!` или перед ним `@` — `// TODO`, `todo: x`, `Fixme(bob)`, `todo!()`,
  `@todo`. Не считаются `todos`, `TODO_LIMIT`, `todo_hits`, `hackathon`, `a todo list`.
  Раньше считалось любое вхождение TODO/FIXME/HACK в любом регистре: на дереве 1.4.0 этого
  репозитория 124 строки, почти все — слово «todos» в документации и имена вроде `todo_hits`;
  теперь 37, и все они — маркеры заглавными (тестовые данные и описание самой команды).
  Новый маркер — XXX.
- `todos --loose` и аргумент MCP `loose: true` — прежнее поведение (подстрока, любой регистр,
  без XXX). API: `todos(root, TodoMatch)`, `TodoMatch::{Strict, Loose}`.

### Документация

- `help extract` (номера строк, поля `lines`/`spans`), `help navigation` (`--exact` с
  примером WRONG/RIGHT, правила `todos`, `--loose`, аргументы MCP), `help mcp`,
  `help overview`, `HELP.md`, README; описания инструментов MCP `extract`, `find_symbol`,
  `todos`.

- **[контракт]** Скан (`map`, навигаторы, кэш, `search`, `todos`, MCP) всегда пропускает
  собственные файлы navguard: кроме навигаторов и `.navguard_cache.json` теперь

## 1.3.0 — 2026-10-19

Границы корня проекта, честные строки и токены, навигаторы со связанными указателями,
безопасный `nav --patch`. Поводом стал сравнительный отчёт по 1.1.0: всё подтвердившееся
на 1.2.0 исправлено. «Раньше» — выпущенный 1.2.0. Тесты — `tests/root_bounds.rs` (через
настоящий exe) и модульные тесты navguard (`paths`, `text`, `scanner`, `navigator`, `cli`).

### Границы корня

- **[контракт]** Команды навигации (`map`, `symbols`, `find`, `lines`, `search`, `todos`,
  `changes`) читают только внутри `--root` (по умолчанию текущая папка). Раньше без `--root`
  корнем становилась папка самого файла, и `lines C:\Windows\win.ini 1 2` читал любой файл.
  Путь наружу (`..`, абсолютный путь в другое место, symlink или junction, ведущий наружу) —
  код 3, `path is outside the project root <корень>: <путь>`.
- **[контракт]** MCP: `mcp --root ПАПКА` задаёт корень сервера (сервер переходит в неё;
  без ключа — рабочая папка). Аргумент `root` инструментов, файлы `read_lines`/`symbols`/
  `search_text`, вход и шаблон `extract`, путь `recon` должны лежать внутри него, иначе
  `isError: true`. Маска входа не может выйти наружу (`..` после `*` запрещено), каждый
  найденный файл проверяется после разрешения ссылок. Раньше `read_lines` без `root` читал
  любой абсолютный путь.
- **[контракт]** `nav` пишет и читает только внутри корня: `--lines`, `--extract`, `--patch`,
  `--build` (план, источники и цели), `--validate` (файлы из `anchor_map.md`). `--set-rules`
  пишет `.navguard_rules` в корень (раньше — в текущую папку), `--triangle` берёт файл
  состояния и журнал в корне (раньше — относительно текущей папки, мимо `--root`).
- **[контракт]** Обход проекта (map, навигаторы, кэш, поиск) не заходит в symlink и junction.
  Раньше junction внутри проекта на внешнюю папку добавлял в карту её содержимое.

### Строки, токены, бинарные файлы

- **[контракт]** navguard считает строки по правилу парсера: LF, CRLF и одиночный CR — конец
  строки; пустой файл — 0 строк; последний перевод строки не добавляет строку. Раньше —
  «переводы строк + 1»: `one\ntwo\nthree\n` давал 4, пустой файл 1. Одиночный CR теперь конец
  строки и для `lines`, `search`, `todos`, `symbols` (ограничение 1.2.0 снято).
- **[контракт]** Токены — оценка с запасом: примерно один на 3 байта UTF-8 (4-байтовый символ
  — 2). Раньше «строки × коэффициент расширения», что занижало в разы (`runner.py` 97 КБ —
  «2992 токена»). Оценка символа в `symbols`/deep2 — по тексту его строк (раньше «непустые
  строки × 1.5»). `token_coeff` в `navguard.json` больше не используется.
- **[контракт]** Бинарные файлы (NUL в первых 8 КиБ, кроме UTF-16 с BOM) — без строк и токенов:
  `map` пишет `binary, N bytes`; в JSON у файла новые поля `bytes` и `binary`.
- `navguard.json` и файл состояния треугольника с BOM читаются (раньше BOM молча давал
  настройки по умолчанию и треугольник `[0,0,0]`).

### Навигаторы

- **[контракт]** `navigator.md`, `navigator_deep.md`, `navigator_deep2.md` собираются в памяти
  из одного чтения каждого файла (размер, строки, sha и символы из одних байтов) и пишутся
  атомарно: deep2, deep, navigator. Раньше deep2 заново читал файлы с диска.
- **[контракт]** `navigator.md`: `Root:` — абсолютный путь корня (раньше `Target: .`),
  `Updated:` — системные дата и время скана с часовым поясом (раньше времени не было),
  `Triangle: [0,1,0]` — READY по ТЗ §15 (раньше `abc:` — состояние рабочего цикла, которое
  сразу после скана показывало `[0,0,1]`), итоги, памятка «как читать» и дерево; у каждого
  файла указатель `deep L<n>`. Таблица FILES убрана (она дословно повторяла deep).
- **[контракт]** `navigator_deep.md`: строка на файл в порядке дерева — имя, байты, строки,
  токены, sha, `deep2 L<a>-L<b>`. `navigator_deep2.md`: секции только у файлов с символами,
  заголовок `### имя  (deep L<n>)`, столбцы Symbol, Kind, Lines, Tokens, In. Полный путь —
  только в дереве (Root + папки); в deep и deep2 — имена файлов, одинаковые имена различаются
  указателями. Заголовок «from anchor_map.md» и повтор протокольных якорей из `anchor_map.md`
  убраны (они и так находятся как `[sX]…[sXend]`).

### `nav --patch`

- **[контракт]** `replace`, `insert`, `delete`: код 1 и ничего не записано, если текст не
  найден, номер строки вне файла, путь вне корня, файл бинарный или не UTF-8. Раньше
  `replace` без совпадения давал код 0.
- `--dry-run` печатает изменение (`-`/`+` строки с номерами) и ничего не пишет.
- Переводы строк файла (CRLF, CR) и BOM сохраняются; многострочный `<old>` с LF находит текст в
  CRLF-файле. Раньше `insert`/`delete` переводили весь файл в LF и всегда добавляли перевод
  строки в конце. Запись атомарная (временный файл и переименование).
- Пустой `<old>` — ошибка (раньше вставлял `<new>` между всеми символами).

### Прочее

- `help --help`, `nav --help`, `nav -h`, `nav help`, `nav --patch help` печатают справку с
  кодом 0 (раньше — ошибка).
- `nav` возвращает код выхода режима; у `--validate`, `--merkle-verify`, `--triangle` с ошибкой
  — 1, как и раньше.
- README: подключение MCP с `--root`, раздел «It stays inside the project», текст лицензии MIT
  (README едет вместе с exe в `dist\`).

### Известные ограничения (не исправлено в 1.3.0)

- CLI `extract` и `recon` читают то, что им передали, без ограничения корнем (у них нет
  `--root`); в MCP они ограничены корнем сервера.
- Исключения обхода — только список `exclude` в `navguard.json` (подстрока имени, по
  умолчанию `.git`, `target`, `node_modules`, `__pycache__`); `.gitignore` не читается, служебные
  папки других инструментов (например `.zvec-grep`) нужно добавить в `exclude`.
- `nav --patch replace` меняет все вхождения; проверки «ровно одно вхождение» нет, `--dry-run`
  показывает их число.
- Абсолютные пути сборочной машины (`cargo-home\registry\...`) остаются в exe в сообщениях
  паник зависимостей.
- Пункты 1.2.0 про экранирование Markdown в метаданных, `--max-block-chars` для разбитой группы
  и пункты 1.0.4 про XML `inner_html`/`outer_html`, `&lt;` в сущностях и числа JSON больше 2^53
  остаются в силе.

## 1.2.0 — 2026-10-19

Исправлены «известные ограничения» из 1.0.4 (кроме трёх последних пунктов того списка).
Версия минорная, потому что меняется контракт вывода: другие данные, новые строки и столбец
документа, другой вид метаданных. «Раньше» — выпущенный 1.1.0. Регрессионные тесты —
`tests/known_limits.rs` (каждый падает на 1.1.0).

### Данные

- **[контракт]** `document.stable_deduplicate` сравнивает значения до обрезки
  `max_item_chars`. Раньше сравнивались уже обрезанные значения, и разные записи с общим
  началом удалялись как дубликаты (потеря данных): `aaaaaaaaaaX`, `aaaaaaaaaaY` при
  `max_item_chars: 10` давали один item, теперь два. Настоящие повторы удаляются как раньше,
  строка `N truncated item(s) dropped as duplicates by stable_deduplicate` осталась (§8).
- **[контракт]** Одно правило переводов строк для всех форматов: LF, CRLF и одиночный CR
  (старый Mac) — конец строки. Декодированный текст сразу приводится к LF, до определения
  формата. Поэтому файл только с CR — это несколько строк, а не одна (`line:`, `contains`,
  `ends_with`, контекст, `recon` видят те же строки), а `\r` из CRLF больше не попадает в
  исходные фрагменты XML (элемент, `inner_html`) и другие значения, копирующие текст
  источника. CR из окончаний строк в документе нет, поэтому номера строк `## Block Index`
  не расходятся у читателей, которые считают одиночный CR концом строки. CR внутри значения
  (JSON `"\r"`, XML `&#13;`) — данные, он сохраняется (§6).
- **[контракт]** Таблицы TOML сохраняют порядок ключей файла (у `toml` включён
  `preserve_order`): `pool = { min = 2, max = 16 }` → `{"min":2,"max":16}` (раньше
  `{"max":16,"min":2}`), `$.servers.*` обходит таблицы в порядке объявления (§7.2).
- **[контракт]** HTML `inner_html`/`outer_html` выводят атрибуты в исходном порядке
  (у `scraper` включён `deterministic`), а не по именам, как в 1.0.4. Вывод по-прежнему
  детерминирован (§7.6).
- **[контракт]** XML с DOCTYPE без расширения `.xml` (plist, маппер MyBatis) при
  `format: auto` определяется как xml: сниффинг разбирает его так же, как адаптер, с
  внутренним подмножеством DTD. Раньше такой файл был text. Файл, чей DTD отклонён
  (`XML DTD rejected: …`, например «бомба» сущностей), тоже xml и получает эту ошибку файла (§6).

### Самоописание документа

- **[контракт]** В `## Execution` после `Run status` — строка `Exit code: N`: код, с которым
  завершился опубликовавший документ запуск.
- **[контракт]** В `## Files` новый столбец `Encoding` после `Status`: кодировка, с которой
  прочитан файл (`utf-8`, `utf-8 (BOM stripped)`, `utf-16le (BOM)`, …; у файла с ошибкой
  декодирования — запрошенная). Подстроки вида `| json | success |` по-прежнему находят
  строку. Числовой столбец `Size` выровнен вправо (раньше — `Modified`).
- **[контракт]** Родитель разбитой группы показывает в `Items:` число item'ов всей группы
  (фрагменты одного item — один item; раньше `Items: 0`), а вместо `(no data)` —
  `(in the continuation parts)`. То же число — в столбце `Items` строки родителя в
  `## Block Index` (§8).
- **[контракт]** У блока `rule not applicable` в `### Warnings` указана причина:
  `rule not applicable: selector type css does not apply to json files (they take jsonpath,
  path)`. То же предупреждение — в результатах `extract`/MCP с `--include-empty` (§7.9).
- **[контракт]** Applied Template показывает `Extract: attr:href` (`inner_html`,
  `outer_html`), если режим задан (`text` по умолчанию не пишется, как в Effective
  Template). Селектор markdown записан как в сокращённом правиле: `heading:^Уст`, `list_item`
  (раньше `node=h pattern="^Уст"`), селектор `line` — `1-20` (раньше `lines 1..=20`).
- **[контракт]** Метаданные экранируются для Markdown минимально, чтобы при рендеринге они
  выглядели как написаны и ничего не скрывали: каждое `<!--` пишется `\<!--` (раньше текст до
  ближайшего `-->` становился комментарием); значение, которое начинает строку или пункт
  списка и начало бы там блок (`## x`, `> x`, `- x`, `1. x`, `---`, ограждение кода, `<…`,
  строка-разделитель таблицы, определение ссылки), получает `\` перед этим знаком
  (`Selector:` → `\## x`, `1\. x`); `|` в ячейках таблиц пишется `\|` и больше не ломает
  строку `## Files`/`## Block Index`. Однострочность и экранирование анкоров сохранены,
  данные не экранируются никогда (§9).

### Навигация

- **[контракт]** `search` (и MCP `search_text`) по умолчанию выводит в файлах кода и данных
  всю обрезанную строку совпадения, одно попадание на строку; в прозе (`.md`, `.txt`, `.rst`,
  `.adoc`, `.org`, `.tex`) — предложение, как раньше. Раньше предложение выводилось везде, и
  на коде строка резалась на каждой точке (`get("port").`). Новая опция `--context
  auto|line|sentence` (MCP: `context`). API navguard: `search_text(…, SearchContext)`.

### Известные ограничения (не исправлено в 1.2.0)

- navguard (`map`, `symbols`, `lines`, `search`, `todos`) делит строки только по LF/CRLF:
  файл только с CR для него одна строка (парсер и `recon` видят несколько).
- Экранирование Markdown в метаданных не трогает инлайн-разметку (`*x*`, `` `x` ``,
  `[a](b)`, HTML-теги кроме комментариев): при рендеринге она оформляется, но текст виден.
  Данные не экранируются: `<!-- x` в item'е при рендеринге открывает HTML-блок до ближайшего
  `-->` (в сыром тексте всё на месте).
- Минимальный работающий `--max-block-chars` для разбитой группы вырос на 18 символов
  (текст родителя `(in the continuation parts)` длиннее `(no data)`).
- Пункты 1.0.4 про XML `inner_html`/`outer_html` (ссылки на внутренние сущности не
  раскрываются), `&lt;` в значении сущности в атрибуте и дробные числа JSON больше 2^53
  остаются в силе.

## 1.1.0 — 2026-10-19

Одна портативная программа для ИИ-агентов: извлечение данных и навигация по проекту
в одном exe, с командами-ключами, MCP-сервером и встроенной справкой на английском.
Режим отчётов `-i -t -o` работает как раньше, его вывод побайтно не изменился.

### Новое

- **Команды** (`any_txt_parser <команда>`, ответ в stdout, `--json` для структуры):
  `extract` (правила прямо в аргументах: `-r contains:ERROR`, `-r "jsonpath:$.a[*]"`,
  повторяемый `-r`, или `-t шаблон`), `recon` (формат, кодировка, структура и первые строки
  файлов, ничего не извлекая), `map`, `symbols`, `find`, `lines`, `search`, `todos`,
  `changes` (навигация по проекту), `nav` (полная командная строка navguard), `mcp`,
  `help [тема]`. Без аргументов программа печатает список команд (код 3).
- **Короткие правила `TYPE:EXPR`**: contains, starts_with, ends_with, regex, jsonpath, path,
  xpath, css, line (`line:10-20`), markdown (`markdown:heading:^Install`). Выражение берётся
  как есть, после первого `:`. Короткое правило читает только файлы тех форматов, которые
  содержат его вид данных, остальные пропускает с заметкой (не предупреждением).
- **Ответ `extract` для ИИ**: результаты без совпадений не выводятся, а считаются в заметке
  (`--include-empty` возвращает их); файл не считается частичным из-за того, что правило в нём
  ничего не нашло; правило, не нашедшее ничего ни в одном файле, — предупреждение, код 1.
  Пути выводятся с `/`. `--max-output-chars` ограничивает объём ответа и говорит, где
  остановился.
- **MCP-сервер** (`any_txt_parser mcp`, JSON-RPC через stdio, протоколы 2024-11-05 …
  2025-06-18): десять инструментов — `help`, `recon`, `extract`, `map`, `symbols`,
  `find_symbol`, `read_lines`, `search_text`, `todos`, `changes`. По умолчанию ответы
  ограничены (50 000 символов данных, 1000 файлов, 200 совпадений, 2000 строк). Все
  инструменты только читают, кроме `changes` с `persist: true`.
- **Встроенная справка** на английском с примерами (`help`, темы overview, extract, rules,
  recon, navigation, mcp, reference) и `README.md`; `README.md` кладётся в `dist\` рядом с exe.
- **navguard внутри**: модуль `crates/navguard` (прежний отдельный navguard 0.1.0).
  Исправлено по рецензии: поиск символов видит вложенные методы, больше языков и видов
  (Rust `pub(crate)`, trait, type, macro; Python async; JS/TS export, interface, стрелочные
  функции; Go; C/C++/Java/C#/Kotlin), границы символов по скобкам для языков со скобками;
  дерево строится из списка просканированных файлов, с `/` и правильными ветками; поиск в
  середине строки больше не сдвигает номер строки; тесты navguard проходят параллельно.
- `LICENSE` (MIT).

## 1.0.4 — 2026-10-18

### Коды выхода и статусы (§4, §7.9)

- **[контракт]** Запуск, в котором **все** входные файлы получили статус `error`, завершается
  кодом `3` (раньше `1`). Документ при этом публикуется: `Run status: failure`, ошибки по
  файлам в `## Diagnostics`; в stderr — `any_txt_parser: no input file could be processed
  (N of M failed); the errors are listed under Diagnostics in '<out>'`, даже с `-q`.
  Ошибки CLI с кодом 3 по-прежнему ничего не публикуют и не трогают документ прошлого
  запуска с тем же `-o`, поэтому различать эти два случая нужно по stderr, а не по наличию
  документа.
- **[контракт]** Статус файла `error` теперь значит «из файла ничего не извлечено»: ошибка
  чтения, декодирования, парсинга или упали все правила, которые к нему выполнялись
  (правила `rule not applicable` не считаются). Ошибка одного правила рядом с работающими
  даёт файлу `warning` (раньше `error`).
- **[контракт]** `Run status: failure` — только когда все файлы `error`. Один упавший файл
  среди успешных теперь даёт `partial_success` (раньше `failure`, при коде 1).
- **[контракт]** `when.format` стал фильтром: для файлов другого формата правило
  пропускается без блока, без предупреждения и без влияния на статус файла. Раньше такие
  файлы получали блок `rule not applicable`, статус `warning` и код 1, поэтому шаблон на
  несколько форматов не мог завершиться с кодом 0. В `## Result Semantics` появилась фраза
  `A rule with "Applies to format" runs only on source files of that format; …`.
- **[контракт]** `when.format`, отличный от фиксированного формата (`--format` или
  `input.format` шаблона), больше не ошибка шаблона (раньше код 2:
  `when.format 'json' contradicts resolved input format 'text'`). Правило просто не
  применяется в этом запуске; это отмечено в `## Applied Template`
  (`Applies to format: json (never applies in this run: …)`), в плане `--dry-run` и при `-v`
  (`Rule 'x' never applies: …`). Поэтому `## Effective Template` запуска с `--format`
  пригоден для повторного использования.
- Новое: если фиксированный формат исключает все правила, каждый прочитанный файл
  получает `warning` (код 1), первая строка `## Diagnostics` —
  `No rule applies in this run: …; nothing was extracted`, то же в `## Result Semantics`,
  в stderr (`any_txt_parser: warning: …`, кроме `-q`) и в `--dry-run`.

### Обрезка трансформациями (§7.7)

- **[контракт]** `truncate_chars`, `truncate_lines` и `limit_items`, если они что-то
  отрезали, считаются обрезкой: `Truncated: yes`, файл `warning`, запуск `partial_success`,
  код 1 (раньше `Truncated: no` и код 0). Каждый такой шаг даёт одну строку в
  `### Warnings` и `## Truncation`, после строк лимитов:
  `3 item(s) truncated by truncate_chars(3): item 1 (8 -> 3 chars), item 2 (8 -> 3 chars); 1 not published`,
  `1 item(s) truncated by truncate_lines(2): item 1 (5 -> 2 lines)`,
  `4 item(s) omitted by limit_items(1)`. Если обрезанные item'ы затем склеены `join`, строка
  выглядит как `item 1 (3 joined items cut to 3 chars)`; обрезка уже склеенного значения даёт
  обычную форму `item 1 (30 -> 3 chars)`.
  Номера — позиции опубликованных item'ов (после последующих трансформаций, `max_items` и
  `stable_deduplicate`); «not published» — обрезанные item'ы, удалённые позже.

### JSONPath по RFC 9535 (§7.1)

- **[контракт]** Сравнение с отсутствующим полем: `!=` даёт true (записи без поля больше не
  отбрасываются молча), `==`, `<`, `<=`, `>`, `>=` — false, два отсутствующих поля равны.
- **[контракт]** Фильтр `[?(...)]` на объекте выбирает подходящие значения его членов в
  исходном порядке (раньше — ничего): `$.services[?(@.enabled == true)].port`.
- Десятичные и экспоненциальные литералы в фильтрах (`1.5`, `-2.25`, `1e3`, `1E+3`,
  `2.5E-2`); раньше `@.t > 1.5` давал ошибку шаблона. Сравнение целых и double точное.
  Ошибка шаблона (код 2): `1.`, `.5`, `+1`, `1e`, переполнение `1e400`, ненулевые литералы,
  уходящие в 0 (`1e-400`), целые вне [-2^63, 2^64) (раньше молча округлялись бы).
- **[контракт]** `<=`/`>=` означают «`<`/`>` или `==`» (`@ <= true` выбирает `true`,
  `@ >= null` — `null`); `==`/`!=` сравнивают массивы и объекты структурно.
- **[контракт]** Строки в кавычках (`['имя']`, литералы, `@['k']`) декодируют
  `\\ \/ \b \f \n \r \t \uXXXX` (с суррогатными парами) и свою экранированную кавычку.
  Обратный слэш больше не буквальный: ключ `a\b` теперь пишется `$['a\\b']`, а прежняя
  запись `$['a\b']` молча ищет ключ с символом backspace (`\b` — допустимый escape). Неизвестный
  escape (`\x`, `\d`), чужая кавычка, неполный `\u`, непарный суррогат и незакрытая строка —
  ошибка шаблона (код 2). Селектор `path` escape-последовательности не раскодирует.

### HTML (§7.4, §7.6)

- **[контракт]** `extract: text` читается как в браузере: inline-теги не вставляют пробел
  (`H<sub>2</sub>O` → `H2O`, раньше `H 2 O`); пробелы разметки сворачиваются
  (`a\n     b` → `a b`); блочные элементы и `<br>` дают переводы строк (`<p>A</p><p>B</p>` →
  `A\nB`, раньше `A B`); ячейки строки таблицы разделяются табуляцией, у пустых ячеек
  табуляция сохраняется; текст `script`, `style`, `noscript`, `template`, `head`, `title`,
  fallback-содержимое `iframe`/`video`/`audio`/`canvas` в текст предка не попадает
  (раньше попадал). Выбранный напрямую `script`/`title` по-прежнему даёт свой текст;
  `head` — пустое значение.
- **[контракт]** Совпадения с пустым значением (пустой текст, пустой `inner_html`,
  `alt=""`) публикуются как item и считаются в `Items:` (раньше молча отбрасывались, и
  правило могло получить `no matches found`). Для удаления — `drop_empty`. Элемент без
  атрибута по-прежнему item не даёт.

### XML (§7.3, §7.6)

- **[контракт]** `extract: attr:NAME` на xpath, оканчивающемся элементом, возвращает
  значение атрибута (как `/@NAME`, без trim, пустое — item, отсутствующий — нет item,
  префиксы корня работают: `attr:xml:lang`). `extract: inner_html` — точный исходный текст
  между тегами. Раньше оба режима игнорировались и возвращалась разметка всего элемента.
- **[контракт]** Режимы `attr:`/`inner_html`/`outer_html` на xpath, оканчивающемся на
  `@attr` или `text()`, а также `attr:` без имени или `attr:@id` — ошибка шаблона (код 2).
- XML с DOCTYPE (plist, XHTML, MyBatis, конфиги) больше не отвергается
  (`invalid XML: XML with DTD detected`): внутренние сущности раскрываются в тексте и
  атрибутах, внешние DTD и сущности никогда не загружаются (`&nbsp;` из DTD XHTML —
  ошибка файла `unknown entity reference`). Опасные DTD отклоняются до разбора как ошибка
  файла `XML DTD rejected: …`: раскрытие более 8 MiB, копирование более 1 GiB текста,
  более 64 Mi сравнений сущностей или 1 GiB сравниваемых имён, вложенность более 10,
  рекурсия, несбалансированная разметка в сущности.
- Лимит глубины 128 учитывает элементы из сущностей
  (`… (entity 'deep' adds 100 levels of elements)`).
- **[контракт]** Имена без префикса в XPath совпадают и с элементами namespace по
  умолчанию, объявленного на корне (pom.xml, Atom, SVG, XHTML): `/project/version/text()`
  теперь работает на pom.xml (раньше — `no matches found`). Элементы с `xmlns=""` считаются
  элементами без namespace. Namespace по умолчанию ниже корня именами без префикса не
  выбирается.

### YAML (§6, §7.2)

- Файлы из нескольких документов `---` обрабатываются (раньше ошибка файла
  `deserializing from YAML containing more than one document is not supported`): каждое
  правило выполняется на каждом документе, результаты — в порядке документов. Пустые и
  `~`-документы пропускаются, якоря не действуют между документами, ошибка в документе
  N ≥ 2 — `invalid YAML in document N: …`. Завершающий `---` (`a: 1\n---\n`) больше не
  ошибка.
- **[контракт]** Merge-ключи `<<: *a`, `<<: [*a, *b]` раскрываются до поиска: свои ключи
  важнее, более ранний источник важнее позднего, цепочки раскрываются, ключи встают на
  место `<<`; ключа `<<` в выводе больше нет. `<<` со значением не-отображением
  (`<<: 5`, `<<: ~`) остаётся обычным ключом; кавычки не важны (`"<<": {a: 1}` сливается).
- **[контракт]** Сниффинг: текст из нескольких документов `---` без расширения определяется
  как yaml, если каждый непустой документ похож на конфиг; документ только из комментариев
  `#` считается пустым (так front matter с телом из одних заголовков `# …` теперь тоже yaml).

### Effective Template (§8, §9)

- **[контракт]** `## Effective Template` — валидный шаблон в каноническом виде: его можно
  сохранить в `.yml` и передать в `-t` без правок, он компилируется в ту же конфигурацию.
  Изменился вид: `line` пишется как `{type: line, from, to}` (было
  `expression: "lines N..=M"`), `markdown` — как `{node, pattern}` с каноническим именем
  узла (было `expression: "node=… pattern=…"`), `regex_replace` — как `{from, to}` (было
  `{pattern, replacement}`), числовой `expression` у `contains` сохраняется (`'404'`, было
  пусто), многострочные строки — в двойных кавычках с `\n` (было `|-`).
- **[контракт]** Строки с текстом анкора в Effective Template пишутся в двойных кавычках с
  `:` как `\x3A`, поэтому общее экранирование анкоров их не затрагивает и декодировать
  YAML перед повторным использованием больше не нужно. Обычные шаблоны выводятся так же,
  как раньше.

### unescape (§7.7)

- **[контракт]** Суррогатная пара из двух escape (`\uD83E\uDD80`) даёт один символ (🦀);
  раньше обе половины пропадали.
- **[контракт]** Ничего не теряется: одиночный или непарный суррогат, `\uZZZZ`, `\u12`,
  `\u+041`, `\u{41}` и `\u` в конце остаются в тексте буквально (раньше `\u` и до четырёх
  следующих символов удалялись, а `\u+041` давал `A`). Текст после невалидного `\u`
  разбирается заново: `\u12\n` → `\u12` и перевод строки.

### Исправления ревью из коммита c91533b (не вошли в выпущенный 1.0.3)

1. **[контракт]** Текст анкора в источниках (`<!-- BLOCK: B0001 END -->`) больше не обрывает
   запуск кодом 4 и не подделывает анкоры: в данных и метаданных каждая
   последовательность `<!-- BLOCK\…:` получает ещё один `\` (обратимо). Внутренняя проверка
   сверяет анкоры построчно за один проход.
2. Файл с расширением `.auto` или без расширения (`json`) определяется сниффингом, а не
   роняет программу паникой (раньше код 101). CLI работает в отдельном потоке со стеком
   64 MiB; любая паника даёт код 5.
3. XML глубже 128 элементов — ошибка файла, а не переполнение стека с падением процесса;
   остальные файлы публикуются.
4. **[контракт]** Обрезка `max_item_chars` — одно сводное предупреждение на правило с
   номерами первых пяти item'ов (раньше по строке на каждый item); применяется после
   `max_items`, номера считаются после `stable_deduplicate`; части разбитого блока не
   повторяют предупреждения родителя.
5. Разбиение блоков линейное по числу строк и item'ов (по описанию коммита: 200 000 коротких
   строк — 1,3 с вместо 69 с в отладочной сборке; в release-сборке один item из 200 000
   строк разбивается за 0,1 с против 0,6 с у 1.0.3).
6. `path` принимает заголовки таблиц TOML (`[database].host`, `[servers.alpha].ip`).
   **[контракт]** `$..key`, отрицательные индексы и срезы в `path` — ошибка шаблона (код 2);
   раньше `$..key` молча читался как `$.key` (и обычно давал `no matches found`).
7. **[контракт]** Сниффинг строже: логи, проза и PEM с двоеточиями остаются text (раньше
   строки вида `2026-10-01 12:00:00 ERROR: x` и PEM-сертификаты определялись как yaml);
   строгий TOML проверяется раньше YAML (файл, начинающийся с `[таблица]`, раньше был text);
   YAML — только при «конфигурационной» форме; слишком глубокий XML считается XML, только
   если все теги парные (`<34>` syslog и `<nick>` остаются text).

Также: строковый аргумент командной строки с невалидным Unicode (например, `-i` или
`--format` с непарным суррогатом UTF-16) даёт код 3 с сообщением clap, а не панику с кодом
101; индексы вида `[+1]` в селекторе `path` по-прежнему работают.

### Найдено фаззером (§9)

- Новый `tests/fuzz.rs`: генераторы случайных входов для всех семи форматов и случайных
  шаблонов. Проверяет отсутствие паник, корректность анкоров, строк Block Index и счётчика
  символов, лимиты блоков, независимость данных от разбиения, детерминизм двух запусков и
  повторное использование Effective Template. Длительный прогон:
  `ATP_FUZZ_ITERS=50000 cargo test --release --test fuzz`, повтор случая — `ATP_FUZZ_REPLAY`.
- **[контракт]** HTML `inner_html`/`outer_html` выводят атрибуты в порядке имён. Раньше
  порядок мог меняться от запуска к запуску, то есть вывод не был детерминирован.
- **[контракт]** Метаданные (пути, id правил, ключи, селекторы, сообщения об ошибках, ячейки
  таблиц) пишутся одной строкой: перевод строки внутри значения выводится как `\n`, `\r` как
  `\r`. Раньше сообщение парсера, цитирующее строку источника, могло добавить в документ
  поддельные строки Block Index и заголовки.
- Целые числа больше 64 бит в YAML читаются так же, как в JSON (`1e+29`), в том числе при
  сниффинге.

### Известные ограничения (не исправлено в 1.0.4; кроме трёх последних пунктов исправлены в 1.2.0)

- `document.stable_deduplicate` сравнивает значения после `max_item_chars`: разные записи с
  общим началом могут быть удалены как дубликаты (это отмечается строкой «dropped as
  duplicates», но данные теряются).
- Одиночный CR (старый формат Mac) не считается переводом строки в текстовом адаптере, а `\r`
  из CRLF может попасть в вывод XML-фрагментов.
- TOML-таблицы публикуются с ключами по алфавиту, а не в порядке файла.
- Метаданные не экранируют Markdown: селектор вида `## x` или `<!-- x` в Applied Template
  становится заголовком или комментарием при рендеринге (данные не затронуты, структура
  анкоров и индекса защищена).
- Самоописание: у родителя разбитой группы `Items: 0`; в Applied Template нет режима
  `extract`, markdown-селектор показан в отладочной форме; кодировка каждого файла и код
  выхода в документ не выводятся; у `rule not applicable` не указана причина.
- XML: файл с DOCTYPE без расширения `.xml` при `format: auto` определяется как текст;
  `inner_html`/`outer_html` оставляют ссылки на внутренние сущности нераскрытыми; сущность с
  `&lt;` в значении атрибута — ошибка файла (roxmltree).
- Дробные числа JSON больше 2^53 могут округляться на одну единицу младшего разряда.
