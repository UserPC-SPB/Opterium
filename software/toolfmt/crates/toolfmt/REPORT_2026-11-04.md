# Report: toolfmt — a tool-output formatter and MCP gateway in Rust

Date: 2026-11-04. Final version — toolfmt 3.1.2. Repository `H:\any_txt_parser`, branch master. Package: `dist\toolfmt-3.1.2\`.

## 1. Original task

What I started with was the specification `SPEC_formatter_EN.md`, revision 2. Its author was a colleague, working with a weaker AI; the prototype was written in Python (`formatter.py` + `mcp_gateway.py`, 23 fixtures). Decisions made along the way:

- **Monetization.** We are not selling the product; it stays open (MIT): no obfuscation, keys, or telemetry. The main reason: the standards are written by the user's own AI (this is requirement D3 of the spec), and the runtime is small and easy to replicate. Besides, nobody would install a closed binary that can see every tool's output.
- **The language is Rust,** because direct memory handling is needed. Hence the design: one process, no HTTP and no subprocesses, any_txt_parser connected as a library.
- **The colleague's goal.** Any AI connects to any MCP server, captures the output of its tools once, and writes its own standard for each tool. The standard is bound to the server.tool pair. After that, the output enters the context immediately in the right shape.
- **The colleague's phrase** "Registering a new MCP server never requires creating standards…" made it into the spec and is honored literally.

## 2. What was found in revision 2 (briefly)

The skeleton is reasonable: output is not touched by default, output is never blocked, PRE and POST are separated, there is a loss marker and reference fixtures. The tests were green (23/23), but they only checked that the code repeats its own reference values. At the same time there was exactly one real output per standard, while the spec itself requires 3–5. The main holes:

- **The family fallback standard could not fire.** The reference to the family lived in the tool's standard file, which is exactly the file that is missing when the fallback is needed.
- **The built-in auto-format and the `[passthrough]` header** contradicted D1 and the colleague's phrase.
- **The most common API response shape** — an object with a list and a cursor (`{items: [...], next_cursor}`) — was not handled.
- **`thousands`/`bytes` as text operations** would have mangled every number in a row: `2026 → 2,026`.
- **`truncate_*` on tables** cut lines in the middle, violating I7.
- **The loss marker was taken from the declaration**, not from what actually happened.
- **A second tool with the same name was unreachable** for the agent.
- **Parameters with `_`** are not described in the tool's schema and may collide with real upstream parameters.
- **MCP protocol:** `outputSchema` and `structuredContent` were not taken into account.
- **`str.format`** allows accessing attributes, which violates I9.
- **Pitfalls when reconciling Python ↔ Rust:** `str(5.0)`, the `1e16` format, large integers, `1 == 1.0 == True`, length in bytes instead of characters.

## 3. What was done

A new workspace crate — `crates/toolfmt`, MIT. First version — 3.0.0; in 3.1.0 the tool catalog was added (section 8), in 3.1.1 — extra tests and fixes (section 9); the final 3.1.2 — fixes from the gateway review (section 10). It is a single binary `toolfmt.exe` (about 5.5 MB, release). Volume: about 8 500 lines of Rust in `src/`, 1 700 lines of integration tests, the spec is about 680 lines.

### Gateway (`toolfmt gateway`)

- An MCP server on stdio, in front of every server from `upstreams.json`. The file format matches the ordinary MCP client configuration (`mcpServers`), so it can be copied from a client as-is.
- **Tool names** stay native. If a name is already taken, the tool gets the name `<server>__<tool>`, and nothing is lost.
- **A tool without a standard** returns the result exactly as the server sent it (D1). Upstream errors are never formatted.
- **A broken standard** does not lose the output: the agent gets the raw output plus the line `[fallback:raw] <reason>` (D2).
- **One-shot parameters** `_render`, `_pre`, `_post`, `_template`, `_limit`, `_keys` are stripped before the upstream call. Exception — when the tool itself declares a parameter with such a name.
- `outputSchema` is removed from the tool list, and `structuredContent` is used as a ready typed input.
- **Resilience:** a fallen server is restarted on the next call, `tools/list_changed` is tracked. On Windows, commands like `npx` are found through PATHEXT, and child processes start without a console window.

### Formatting pipeline

DETECT → RESOLVE → ROOT/PRE → RENDER → POST → truncation marks and cursors → header.

- **Renders:**
  - `json` — compact JSON;
  - `expression` — e.g. `2 + 3 = 5`, no eval;
  - `matrix_table`;
  - `objects_table` — TOON or Markdown;
  - `dict_table`;
  - `template` — in-memory any_txt_parser rules;
  - `log` — level counters and unique errors with `×N`;
  - `num_stats` — exact fraction for integers;
  - `tree`;
  - `image_meta` — the format and size of an image, no pixels.
- **PRE operations:** `unique`, `sort`/`sort_desc` (by key), `limit_items`, `select`.
- **POST operations:** `join`, `replace`, `truncate_*`, `drop_lines`/`keep_lines`, `mask`.
- **Value formats** `thousands`, `bytes`, `fixed:N` are applied only to numbers inside cells.
- **Numbers and keys are never distorted.** Numbers pass through exactly as upstream wrote them: `5.0`, `1e16`, 30-digit integers. Key order is preserved. Call arguments reach upstream with the same digits.
- **Pagination cursors** never disappear (I8). **Every truncation** is declared with a line of the form `… 37 more rows` (I3).
- **Regular expressions** run on a linear-time engine: hangs are impossible, timeouts are unnecessary, output is deterministic.

### How the agent creates standards itself

1. The agent calls the tool; the first real outputs are saved to `fixtures/` (secrets are masked).
2. `formatter_inspect` shows the tool's outputs and help on the standard format.
3. `formatter_save_standard` checks the standard, runs it over all captured outputs, shows the result, and saves it. Without a captured output, a standard is not saved (D3).
4. The next call already arrives formatted.

To capture samples the gateway itself makes no calls, so destructive tools are never touched. Tools marked `readOnlyHint` are listed as safe for a first call.

### Other modes

- `serve` — the old HTTP contract `POST /clean`, so the Python adapter can work with the Rust formatter unchanged;
- `clean`, `format` — format a single output from the command line;
- `replay` — run the fixture corpus against the reference values;
- `check` — validate the standards;
- `demo-server` — a demo server with typical output shapes.

The call log `audit.jsonl` is written to the home folder. Writing goes only there (I4).

### A fix inside any_txt_parser itself

Found while testing toolfmt. The parser's JSON adapter read numbers through serde_json, and long integers were rounded: `12345678901234567890` became `1.2345678901234568e+29`. In addition, the notation changed (`1E16 → 1e+16`).

Now the adapter stores the source text of each number. The `arbitrary_precision` flag was not suitable: it changes deserialization across the whole crate and rewrites the exponent itself. The fix was made in a separate session and checked before merging.

## 7. What was not done and the limits

- **Verification on the colleague's servers** (cube_v5 and others, 123 tools) and the import of his Python corpus are still ahead. For that his `upstreams.json` and `fixtures/` folder are needed.
- **Byte-for-byte compatibility with the Python version is not the goal.** Revision 3 changes behavior deliberately: an untouched output has no header, TOON by default, the `thousands` and `bytes` formats are applied to values. Old fixtures are read as-is, and the difference is visible through `toolfmt replay`.
- **Not implemented:**
  - rating images with a local model and downscaling images;
  - HTTP upstream (only stdio servers are supported);
  - standards that depend on the call arguments;
  - a store for large outputs.

  All of this is listed in section 15 of the spec (Roadmap).
- **The gateway is for tools only.** The servers' resources and prompts are not aggregated. The server's requests to the client (sampling, elicitation) are not forwarded and receive an error; `roots/list` — an empty list. A server that needs that will not work through toolfmt. This is noted in the README and the spec.
- **Nothing has been published** to Opterium or to GitHub.

## 8. Added after the report: the tool catalog (toolfmt 3.1, the colleague's idea)

The colleague proposed: one MCP module hands the AI a tree of sections (mathematics `2_187`, images, eyes, browser, parsers…), where the first two digits are the number of nested modules and the total number of tools. The AI picks the tools it needs and gets for them the metadata, the average price, and the methods. This was done in the gateway.

**Why.** The schemas of all tools go into the model with every request. With 34 tools (any_txt_parser and two demo servers) that is 13 708 characters per request. In catalog mode it stays at 1 988 (−85%), and a specific tool's schema is paid for once, when the agent requests its card. With the colleague's 123 tools the gain would be many times larger.

**How it works.** Instead of all tools, the list keeps:
- `catalog` — the tree, search, and cards;
- `call_tool` — a call of any tool by name;
- pinned tools (`pin`) as ordinary ones;
- the two formatter tools.

The `expose` mode: `all`, `catalog`, or `auto`. In `auto` (the default) the catalog switches on when there are more than 30 tools; otherwise the list stays flat.

| What the colleague asked for | How it was done |
|---|---|
| A section tree `math 2_187` | `section` on the server (nesting via `/`), `groups` by name masks. A large section (more than 20 tools) splits itself by name prefix. The section description is taken from `sections` or from the server's own `instructions` |
| Tool descriptions, choosing the needed ones | `catalog path=…` shows a section, `catalog query=…` searches by words (best 15) |
| Metadata and methods | The card: call signature `search_text(root?: string, pattern: string, …)` instead of a JSON schema, parameter descriptions, read-only and dangerous-tool hints, what formats the output, an example of arguments from a real captured call |
| Average price | Measured: number of calls, average output size before and after formatting, average time, errors — from the call log, with past sessions included. The monetary price for paid APIs is set in the config (`price`, `prices`) |

Beyond the colleague's idea:
- search: the needed tool is found in one call, without descending the tree;
- `call_tool` itself checks required arguments and answers with a signature;
- on an unknown name `call_tool` suggests similar tools;
- pinned tools are called without an extra step;
- the `auto` mode keeps small tool sets flat.

This is the same principle on which Claude Code itself works: deferred tools that are loaded through search.

Verification: the catalog's unit tests and an end-to-end catalog-mode test with two demo servers. The test checks:
- the short tool list;
- the tree with numbers and descriptions;
- search;
- `call_tool` with arguments as an object and as a string;
- cards with price and example;
- name collisions;
- the answer to a missing argument;
- persistence of the measurements after a restart.

Details — in section 2.1 of the spec.

## 9. Extra tests and fixes (toolfmt 3.1.1)

There were too few tests in 3.1.0 for a tool that sits between the agent and all tools: mostly the happy path was checked. Added:

| Set | What it checks |
|---|---|
| `tests/failures.rs` (9) | a server dying mid-call and the restart; a timeout after which the connection stays alive; junk and broken UTF-8 in the server's stdout; broken bytes from the client; the server's requests to the client (roots, sampling); paged `tools/list`; `list_changed` from the server reaches the client; 120 parallel calls on two servers; a 10 MB output through the gateway |
| `tests/http.rs` (2) | `serve` mode: health, `/clean` with and without a standard, a body over 1 MB with Cyrillic text, refusal on `Origin`, broken JSON, 404, parallel requests |
| `tests/renders.rs` (14) | all renders, modes, and operations on exact small examples |
| `tests/fuzz.rs` (3) | 5 000 round-trip checks of JSON, 20 000 random and truncated strings into the parser, 12 000 runs of all renders on random data — not a single panic |

For the demo-server failure modes there is now a `--test-modes` flag with the tools `crash`, `sleep`, `noise`, `ask_client`, `grow`, `big`.

**Found and fixed:**

1. **Broken UTF-8 tore the connection.** One non-UTF-8 line in the server's stdout cut the connection to it, and the following calls failed. Confirmed on the released 3.1.0 binary. The same was true on the input stream from the client: a broken line terminated the gateway itself. Now such a line is skipped.
2. **Orphan process.** After a stream break, the child process kept hanging around. Now the gateway terminates it.
3. **Memory.** An output without a standard was fully parsed into a tree. Capturing a sample copied and serialized the whole output before checking the limit. The response to the client was first assembled into one big string. The read buffer stayed inflated after a large message. All fixed. Untouched output of 31 MB: peak 254 → 67 MB (−74%), time 0.73 → 0.5 s. After the call memory returns to 6 MB (was 37).
4. **False precision.** On overflow `num_stats` printed approximate values with 39 digits, as if they were exact. Now in exponential notation.
5. **Configuration.** The pause between server restarts (`restart_backoff`) became configurable.

**Verification in a real environment:**

- **Your servers.** Through the gateway, `davinci-resolve` (python, 37 tools), `local-qwen` (node), any_txt_parser, and the demo server were connected — 60 tools in total. The catalog split DaVinci into the sub-sections project, media, timeline by itself. `qwen_status` was called through `call_tool`, and the answer in Russian passed through undistorted. The tool list in every request: 137 368 characters in flat mode vs. 1 988 in catalog mode (−98.6%).
- **Claude Code CLI 2.1.282.** Connected to the gateway (`connected`) and received the short tool list. The call cycle with the model was not checked: the CLI is not authorized in this environment; your login is needed.

**Numbers** (release, gateway peak memory): at rest — 5 MB; output of 31 MB without a standard — 67 MB and 0.5 s; the same output with sorting and truncation by a standard — 256 MB and 0.7 s.

**What remained:**

- The path with a standard keeps the parse tree; that is about 8× the output size at peak. It can only be reduced by parsing without copying strings — item 8 of the roadmap in the spec.
- Not checked: the model cycle in Claude Code (a login is needed), Claude Desktop and Studio, servers through `npx`/`uvx` (they would have to be downloaded), the colleague's servers.

## 10. Fixes from the gateway review (toolfmt 3.1.2)

Fixed per your review:

1. **Tool names could go to the wrong server.** Names were recomputed against the servers that had already come up. If a server listed earlier in the config started later, it took the bare name `foo`. A call that the agent believed was a call to another server went somewhere else — including for a tool with side effects. Now the name is pinned as soon as the client saw or used it, and it does not change its addressee for the rest of the session. A late server gets `server__foo`. The name of a fallen server stays with it: a call through it restarts that server, instead of reaching someone else's tool. If `server__foo` is taken as well, `_2`, `_3` are added; before, the tool simply disappeared in that case.
2. **Cancels from the client did not reach the server.** Now `notifications/cancelled` is forwarded to the server with its own request number and the client's reason; the client receives no answer to a cancelled call. Pass-through of progress notifications was done at the same time.
3. **Formatting changed the result structure.** The formatted text replaces exactly what the input was built from: structuredContent and its JSON copy, all text blocks, or one described image. The rest stays in its place: other text (for example, "2 items found"), images, resource links, `_meta`, extra fields. Annotations shared by the replaced blocks move onto the new block. Found along the way: `image_meta` removed every image, although it described only the first.
4. **The protocol version was not checked.** The client received any requested version. Now the gateway supports 2025-06-18, 2025-03-26, and 2024-11-05, and answers 2025-06-18 to the rest. A server that answered with an unknown version is disconnected, and `formatter_inspect` shows the reason.
5. **A race on restart.** Several calls could simultaneously decide to restart a fallen server, and the old process remained an orphan. Now the decision and the transition to "starting" are made under one lock.
6. **`formatter_save_standard` saved a non-working standard.** A standard that falls back to the raw output on the samples is now not saved without `force=true`. Errors in writing reference values are no longer lost: the answer states in how many samples the reference value was written and names the failed ones.

New tests: `tests/proxy.rs` (7) and the gateway's unit tests (10). A control run on the old code: 6 of the 7 new integration tests fail exactly on these defects. The seventh, "24 calls after a fall — one restart", passes on the old code: the race window is too short. The unit test catches the race.
