# Отчёт: toolfmt — форматтер вывода тулов и MCP-шлюз на Rust

Дата: 2026-11-04. Финальная версия — toolfmt 3.1.2. Репозиторий `H:\any_txt_parser`, ветка master. Пакет: `dist\toolfmt-3.1.2\`.

## 1. Исходная задача

На входе была спецификация `SPEC_formatter_EN.md`, ревизия 2. Её автор — коллега, работал с более слабой ИИ, прототип написан на Python (`formatter.py` + `mcp_gateway.py`, 23 фикстуры). Решения, принятые по ходу:

- **Монетизация.** Продавать продукт не будем, он остаётся открытым (MIT): без обфускации, ключей и телеметрии. Главная причина: стандарты пишет ИИ самого пользователя (это требование D3 спеки), а рантайм небольшой и легко повторяется. К тому же закрытый бинарник, который видит выводы всех тулов, никто не станет ставить.
- **Язык — Rust,** потому что нужна прямая работа с памятью. Отсюда устройство: один процесс, без HTTP и подпроцессов, any_txt_parser подключён как библиотека.
- **Цель от коллеги.** Любой ИИ подключает любой MCP-сервер, один раз снимает выводы его тулов и пишет под каждый тул свой стандарт. Стандарт привязывается к паре server.tool. После этого вывод попадает в контекст сразу в нужном виде.
- **Фраза коллеги** «Registering a new MCP server never requires creating standards…» вошла в спеку и выполняется буквально.

## 2. Что нашлось в ревизии 2 (кратко)

Каркас разумный: по умолчанию вывод не трогается, вывод никогда не блокируется, PRE и POST разделены, есть маркер потерь и эталонные фикстуры. Тесты были зелёными (23/23), но проверяли только то, что код повторяет собственные эталоны. При этом на каждый стандарт приходился один реальный вывод, а сама спека требует 3–5. Главные дыры:

- **Запасной стандарт семейства не мог сработать.** Ссылка на семейство лежала в файле стандарта тула, а он нужен как раз тогда, когда этого файла нет.
- **Встроенный автоформат и заголовок `[passthrough]`** противоречили D1 и фразе коллеги.
- **Самая частая форма ответа API** — объект со списком и курсором (`{items: [...], next_cursor}`) — не обрабатывалась.
- **`thousands`/`bytes` как текстовые операции** портили бы все числа подряд: `2026 → 2,026`.
- **`truncate_*` на таблицах** резал строки посередине, нарушая I7.
- **Маркер потерь брался из объявления**, а не из того, что произошло на самом деле.
- **Второй тул с тем же именем был недоступен** агенту.
- **Параметры с `_`** не описаны в схеме тула и могут совпасть с настоящими параметрами upstream.
- **MCP-протокол:** `outputSchema` и `structuredContent` не учитывались.
- **`str.format`** позволяет обращаться к атрибутам, что нарушает I9.
- **Ловушки при сверке Python ↔ Rust:** `str(5.0)`, формат `1e16`, большие целые, `1 == 1.0 == True`, длина в байтах вместо символов.

## 3. Что сделано

Новый крейт workspace — `crates/toolfmt`, MIT. Первая версия — 3.0.0, в 3.1.0 добавлен каталог тулов (раздел 8), в 3.1.1 — добор тестов и исправления (раздел 9), финальная 3.1.2 — исправления по ревью шлюза (раздел 10). Это один бинарник `toolfmt.exe` (около 5.5 МБ, release). Объём: около 8 500 строк Rust в `src/`, 1 700 строк интеграционных тестов, спека около 680 строк.

### Шлюз (`toolfmt gateway`)

- MCP-сервер на stdio перед всеми серверами из `upstreams.json`. Формат файла совпадает с обычным конфигом MCP-клиентов (`mcpServers`), так что его можно скопировать из клиента как есть.
- **Имена тулов** остаются родными. Если имя уже занято, тул получает имя `<server>__<tool>`, и ничего не теряется.
- **Тул без стандарта** возвращает результат ровно таким, каким его прислал сервер (D1). Ошибки upstream не форматируются никогда.
- **Сломанный стандарт** не теряет вывод: агент получает сырой вывод и строку `[fallback:raw] <причина>` (D2).
- **Разовые параметры** `_render`, `_pre`, `_post`, `_template`, `_limit`, `_keys` вырезаются до вызова upstream. Исключение — если тул сам объявляет параметр с таким именем.
- `outputSchema` убирается из списка тулов, а `structuredContent` используется как готовый типизированный вход.
- **Устойчивость:** упавший сервер перезапускается при следующем вызове, `tools/list_changed` отслеживается. На Windows команды вроде `npx` находятся через PATHEXT, а дочерние процессы стартуют без окна консоли.

### Конвейер форматирования

DETECT → RESOLVE → ROOT/PRE → RENDER → POST → пометки об обрезке и курсоры → заголовок.

- **Рендеры:**
  - `json` — компактный JSON;
  - `expression` — например, `2 + 3 = 5`, без eval;
  - `matrix_table`;
  - `objects_table` — TOON или Markdown;
  - `dict_table`;
  - `template` — правила any_txt_parser в памяти;
  - `log` — счётчики уровней и уникальные ошибки с `×N`;
  - `num_stats` — точная дробь для целых;
  - `tree`;
  - `image_meta` — формат и размер картинки, без пикселей.
- **PRE-операции:** `unique`, `sort`/`sort_desc` (по ключу), `limit_items`, `select`.
- **POST-операции:** `join`, `replace`, `truncate_*`, `drop_lines`/`keep_lines`, `mask`.
- **Форматы значений** `thousands`, `bytes`, `fixed:N` применяются только к числам в ячейках.
- **Числа и ключи не искажаются.** Числа идут ровно так, как их написал upstream: `5.0`, `1e16`, 30-значные целые. Порядок ключей сохраняется. Аргументы вызова доходят до upstream с теми же цифрами.
- **Курсоры пагинации** не пропадают никогда (I8). **Каждая обрезка** объявляется строкой вида `… 37 more rows` (I3).
- **Регулярные выражения** выполняются движком линейного времени: зависание невозможно, таймауты не нужны, вывод детерминирован.

### Как агент сам заводит стандарты

1. Агент вызывает тул, первые реальные выводы сохраняются в `fixtures/` (секреты маскируются).
2. `formatter_inspect` показывает выводы тула и справку по формату стандарта.
3. `formatter_save_standard` проверяет стандарт, прогоняет его на всех снятых выводах, показывает результат и сохраняет. Без снятого вывода стандарт не сохранится (D3).
4. Следующий вызов приходит уже отформатированным.

Ради снятия образцов шлюз сам ничего не вызывает, поэтому разрушительные тулы не трогаются. Тулы с пометкой `readOnlyHint` перечисляются как безопасные для первого вызова.

### Прочие режимы

- `serve` — старый HTTP-контракт `POST /clean`, чтобы Python-адаптер мог работать с Rust-форматтером без изменений;
- `clean`, `format` — отформатировать один вывод из командной строки;
- `replay` — прогнать корпус фикстур против эталонов;
- `check` — проверить стандарты;
- `demo-server` — демо-сервер с типичными формами вывода.

Журнал вызовов `audit.jsonl` пишется в домашнюю папку. Запись идёт только туда (I4).

### Исправление в самом any_txt_parser

Найдено при тестировании toolfmt. JSON-адаптер парсера читал числа через serde_json, и длинные целые округлялись: `123456789012345678901234567890` превращалось в `1.2345678901234568e+29`. Кроме того, менялась запись (`1E16 → 1e+16`).

Теперь адаптер хранит исходный текст каждого числа. Флаг `arbitrary_precision` не подошёл: он меняет десериализацию во всём крейте и сам переписывает экспоненту. Исправление сделано в отдельной сессии и проверено перед слиянием.

## 7. Что не сделано и ограничения

- **Проверка на серверах коллеги** (cube_v5 и другие, 123 тула) и импорт его Python-корпуса ещё впереди. Для этого нужны его `upstreams.json` и папка `fixtures/`.
- **Побайтная совместимость с Python-версией не цель.** Ревизия 3 меняет поведение специально: у нетронутого вывода нет заголовка, по умолчанию TOON, форматы `thousands` и `bytes` применяются к значениям. Старые фикстуры читаются как есть, а разница видна через `toolfmt replay`.
- **Не реализовано:**
  - оценка картинок локальной моделью и уменьшение картинок;
  - HTTP-upstream (поддерживаются только stdio-серверы);
  - стандарты, зависящие от аргументов вызова;
  - хранилище больших выводов.

  Всё это перечислено в разделе 15 спеки (Roadmap).
- **Шлюз только для тулов.** Resources и prompts серверов не агрегируются. Запросы сервера к клиенту (sampling, elicitation) не пересылаются и получают ошибку, `roots/list` — пустой список. Сервер, которому это нужно, через toolfmt работать не будет. Это записано в README и спеке.
- **Ничего не опубликовано** в Opterium и на GitHub.

## 8. Добавлено после отчёта: каталог тулов (toolfmt 3.1, идея коллеги)

Коллега предложил: один MCP-модуль отдаёт ИИ дерево разделов (математика `2_187`, картинки, глаза, браузер, парсеры…), где первые две цифры — число вложенных модулей и общее число тулов. ИИ выбирает нужные тулы и получает по ним метаданные, среднюю цену и методы. Это сделано в шлюзе.

**Зачем.** Схемы всех тулов уходят модели в каждом запросе. При 34 тулах (any_txt_parser и два демо-сервера) это 13 708 символов на каждый запрос. В режиме каталога остаётся 1 988 (−85%), а схема конкретного тула оплачивается один раз, когда агент запрашивает его карточку. На 123 тулах коллеги выигрыш будет кратно больше.

**Как устроено.** Вместо всех тулов в списке остаются:
- `catalog` — дерево, поиск и карточки;
- `call_tool` — вызов любого тула по имени;
- закреплённые тулы (`pin`) как обычные;
- два тула форматтера.

Режим `expose`: `all`, `catalog` или `auto`. В `auto` (по умолчанию) каталог включается, когда тулов больше 30, иначе список остаётся плоским.

| Что просил коллега | Как сделано |
|---|---|
| Дерево разделов `math 2_187` | `section` на сервер (вложенность через `/`), `groups` по маскам имён. Крупный раздел (больше 20 тулов) сам делится по префиксу имени. Описание раздела берётся из `sections` или из `instructions` самого сервера |
| Описания тулов, выбор нужных | `catalog path=…` показывает раздел, `catalog query=…` ищет по словам (лучшие 15) |
| Метаданные и методы | Карточка: сигнатура вызова `search_text(root?: string, pattern: string, …)` вместо JSON-схемы, описания параметров, подсказки read-only и опасных тулов, чем форматируется вывод, пример аргументов из реального снятого вызова |
| Средняя цена | Измеренная: число вызовов, средний размер вывода до и после форматирования, среднее время, ошибки — из журнала вызовов, с учётом прошлых сессий. Денежная цена для платных API задаётся в конфиге (`price`, `prices`) |

Что сверх идеи коллеги:
- поиск: нужный тул находится одним вызовом, без спуска по дереву;
- `call_tool` сам проверяет обязательные аргументы и отвечает сигнатурой;
- на неизвестное имя `call_tool` предлагает похожие тулы;
- закреплённые тулы вызываются без лишнего шага;
- режим `auto` оставляет маленькие наборы тулов плоскими.

Это тот же принцип, по которому работает сам Claude Code: отложенные тулы, которые подгружаются через поиск.

Проверка: модульные тесты каталога и сквозной тест режима каталога с двумя демо-серверами. В тесте проверены:
- короткий список тулов;
- дерево с числами и описаниями;
- поиск;
- `call_tool` с аргументами объектом и строкой;
- карточки с ценой и примером;
- коллизии имён;
- ответ на пропущенный аргумент;
- сохранение замеров после перезапуска.

Подробности — в разделе 2.1 спеки.

## 9. Добор тестов и исправления (toolfmt 3.1.1)

Тестов в 3.1.0 было мало для инструмента, который стоит между агентом и всеми тулами: в основном проверялся счастливый путь. Добавлено:

| Набор | Что проверяет |
|---|---|
| `tests/failures.rs` (9) | падение сервера посреди вызова и перезапуск; таймаут, после которого соединение остаётся рабочим; мусор и битый UTF-8 в stdout сервера; битые байты от клиента; запросы сервера к клиенту (roots, sampling); постраничный `tools/list`; `list_changed` от сервера доходит до клиента; 120 параллельных вызовов на два сервера; вывод 10 МБ через шлюз |
| `tests/http.rs` (2) | режим `serve`: health, `/clean` со стандартом и без, тело больше 1 МБ с кириллицей, отказ на `Origin`, битый JSON, 404, параллельные запросы |
| `tests/renders.rs` (14) | все рендеры, режимы и операции на точных маленьких примерах |
| `tests/fuzz.rs` (3) | 5 000 круговых проверок JSON, 20 000 случайных и обрезанных строк в парсер, 12 000 прогонов всех рендеров на случайных данных — ни одной паники |

Для сбоев у демо-сервера появился флаг `--test-modes` с тулами `crash`, `sleep`, `noise`, `ask_client`, `grow`, `big`.

**Найдено и исправлено:**

1. **Битый UTF-8 рвал соединение.** Одна строка не в UTF-8 в stdout сервера обрывала соединение с ним, и следующие вызовы падали. Подтверждено на выпущенном бинарнике 3.1.0. То же было с входным потоком от клиента: битая строка завершала сам шлюз. Теперь такая строка пропускается.
2. **Процесс-сирота.** После обрыва потока дочерний процесс оставался висеть. Теперь шлюз его завершает.
3. **Память.** Вывод без стандарта целиком разбирался в дерево. Захват образца копировал и сериализовал вывод целиком, прежде чем проверить лимит. Ответ клиенту сначала собирался в одну большую строку. Буфер чтения после большого сообщения оставался раздутым. Всё исправлено. Нетронутый вывод в 31 МБ: пик 254 → 67 МБ (−74%), время 0,73 → 0,5 с. После вызова память возвращается к 6 МБ (было 37).
4. **Ложная точность.** При переполнении `num_stats` печатал приближённые значения 39 цифрами, будто они точные. Теперь в экспоненциальной записи.
5. **Настройка.** Пауза между перезапусками сервера (`restart_backoff`) стала настраиваемой.

**Проверка на настоящем окружении:**

- **Ваши серверы.** Через шлюз подключены `davinci-resolve` (python, 37 тулов), `local-qwen` (node), any_txt_parser и демо-сервер — всего 60 тулов. Каталог сам разбил DaVinci на подразделы project, media, timeline. `qwen_status` вызван через `call_tool`, ответ на русском прошёл без искажений. Список тулов в каждом запросе: 137 368 символов в плоском режиме против 1 988 в режиме каталога (−98,6%).

## 10. Исправления по ревью шлюза (toolfmt 3.1.2)

По вашему ревью исправлено:

1. **Имена тулов могли уйти к другому серверу.** Имена пересчитывались по тем серверам, что уже поднялись. Если сервер, стоящий в конфиге раньше, стартовал позже, он забирал голое имя `foo`. Вызов, который агент считал вызовом другого сервера, уходил не туда — в том числе для тула с побочными эффектами. Теперь имя закрепляется, как только клиент его увидел или использовал, и до конца сессии не меняет адресата. Поздний сервер получает `server__foo`. Имя упавшего сервера остаётся за ним: вызов по нему перезапускает этот сервер, а не попадает к чужому тулу. Если занято и `server__foo`, добавляется `_2`, `_3`; раньше тул в этом случае просто пропадал.
2. **Отмена от клиента не доходила до сервера.** Теперь `notifications/cancelled` передаётся серверу с его собственным номером запроса и причиной от клиента; на отменённый вызов клиент ответа не получает. Заодно сделан проброс progress-уведомлений.
3. **Форматирование меняло структуру результата.** Отформатированный текст заменяет ровно то, из чего собран вход: structuredContent и его JSON-копию, все текстовые блоки или одну описанную картинку. Остальное сохраняется на своих местах: другой текст (например, «2 items found»), картинки, ссылки на ресурсы, `_meta`, лишние поля. Аннотации, общие для заменённых блоков, переходят на новый блок. Попутно найдено: `image_meta` удалял все картинки, хотя описывал только первую.
4. **Версия протокола не проверялась.** Клиент получал любую запрошенную версию. Теперь шлюз поддерживает 2025-06-18, 2025-03-26 и 2024-11-05, на остальное отвечает 2025-06-18. Сервер, ответивший неизвестной версией, отключается, и `formatter_inspect` показывает причину.
5. **Гонка при перезапуске.** Несколько вызовов могли одновременно решить перезапустить упавший сервер, и прежний процесс оставался сиротой. Теперь решение и переход в «запускается» делаются под одной блокировкой.
6. **`formatter_save_standard` сохранял неработающий стандарт.** Стандарт, который на образцах откатывается к сырому выводу, теперь не сохраняется без `force=true`. Ошибки записи эталонов больше не теряются: ответ пишет, в скольких образцах эталон записан, и называет неудавшиеся.

Новые тесты: `tests/proxy.rs` (7) и модульные тесты шлюза (10). Контрольный прогон на старом коде: 6 из 7 новых интеграционных тестов падают ровно на этих дефектах. Седьмой, «24 вызова после падения — один перезапуск», на старом коде проходит: окно гонки слишком короткое. Гонку ловит модульный тест.
