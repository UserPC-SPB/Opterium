# Отчёт: toolfmt 3.1.3 и `map --name`

Дата: 2026-11-20. Ветка `toolfmt-3.1.3-fixes`, от `b4a4125` (toolfmt 3.1.2). Пакеты: `dist/toolfmt-3.1.3/` (Windows) и `dist/toolfmt-3.1.3-linux-x86_64/` (Linux).

## 1. Откуда изменения

План улучшения toolfmt опирался на замер версии 3.1.2 с Qwen3-VL-30B-A3B в окне 64K. Замер повторён на другой модели и с большим окном: Qwen3.8-Flash-Next UD-IQ4_XS на Strata, 256K. Первый прогон, 72 попытки на 3.1.2, показал три вещи.

- **Причина провалов на большой карте не в окне.** Карта на 1 000 файлов (57 000 токенов) в окно 256K помещается, а точность не выросла. Модель не находит в длинном списке нужную строку и перечитывает карту.
- **Почти все провалы — «7 ходов без ответа».** Модель тратила ходы на `formatter_inspect` и `formatter_save_standard`, включая `dry_run`. Неправильных ответов почти не было.
- **Стенд недосчитывал верные ответы.** Он засчитывал ответ, только если тот был чистым JSON. В 11 из 72 попыток верный JSON шёл после пояснения и считался ошибкой.

Отсюда состав выпуска: исправить гарантии типов и курсоров (этап 1 плана), убрать формат-инструменты из рабочего набора агента, добавить поиск файла по имени у настоящего источника (этап 2, первая строка таблицы).

## 2. Что изменено

### toolfmt 3.1.3

1. **Автотаблица больше не путает типы.** В ячейке вложенный массив `[1,2]` печатался так же, как строка `"[1,2]"`. Объект печатался как строка с тем же JSON. Из повторяющихся ключей показывался один. Теперь встроенный автоформат в таких случаях отдаёт вывод без изменений. Явный стандарт `objects_table` на повторяющемся ключе откатывается к сырому выводу (`[fallback:raw] objects_table: an item repeats a key`). Код: `table_ambiguity` в `src/render.rs`.
2. **Значения в строках `ключ: значение` различимы.** Строка, которая читается как другой тип (`null`, `true`, `42`, `[...]`, `{...}`, `"..."`), берётся в кавычки: `total: null` и `total: "null"` больше не совпадают.
3. **Курсор страниц (I8).** Раньше строка `cursor:` не добавлялась, если имя ключа и значение где-то встречались в тексте, пусть и в разных местах. Теперь рендерер сообщает, какие поля он вывел дословно (`Effect::shown`): строка конверта, весь документ, подстановка `{result.<путь>}` в `expression`. Шлюз верит только этому. Операции POST сбрасывают подтверждение. Формат строки прежний: `cursor: <путь>=<значение>`.
4. **`"formatter_tools": false`** в `upstreams.json`. Формат-инструменты не попадают в `tools/list` и в инструкции, вызов к ним отвечает «unknown tool». Стандарты продолжают применяться. Значение по умолчанию — `true`, поведение прежнее.

### any_txt_parser / navguard

5. **`map --name ИМЯ`** (в MCP — параметр `name`). Возвращает только файлы, у которых последняя часть пути точно равна имени, с учётом регистра. Поиск идёт по всему проекту до ограничения `max_files`, итоги по-прежнему по всем файлам. У каждого совпадения полный относительный путь, число строк и оценка токенов, у двоичных — размер. Дерево не выводится. Если файла нет, это обычный ответ (`no file with this name`), имя с каталогом — ошибка, код 3. В JSON появляются поля `name` и `matched`; у обычной карты их нет, её вывод не изменился. В описании тула есть пример `{"name": "main.rs"}`.

### Что может увидеть пользователь 3.1.2

- В автоформате вывод со вложенными значениями в списке объектов больше не превращается в таблицу и приходит как есть.
- В строках конверта значения вида `"null"` или `"42"` теперь в кавычках.
- Строка `cursor:` может появиться там, где раньше её не было: текст упоминал курсор, а рендерер его не выводил.
- `any_txt_parser.exe` в пакете собран из того же коммита и называет себя `1.5.0`, хотя содержит невыпущенные изменения из раздела «Не выпущено» журнала, в том числе `map --name`. Номер версии парсера не менялся — это решение о выпуске за вами.

## 3. Замер

Условия те же, что в первом прогоне на Strata. Модель Qwen3.8-Flash-Next UD-IQ4_XS, контекст 262 144, thinking выключен. Temperature 0, seed 29, не больше 7 обращений к модели и 300 выходных токенов на ход. Шесть задач, пять профилей, три серии с разным порядком — всего 90 попыток. Ответ засчитывается, если последний JSON в нём совпал с эталоном и в выдаче инструментов были данные для обоснования. Строгая оценка (весь ответ — JSON) приведена отдельно.

**Выводы.**

- **Сокрытие формат-инструментов** дало больше всего: 10/18 → 18/18, расход на подтверждённый ответ в 7,8 раза меньше. Из 13 неудач в профилях raw и addressed 12 — исчерпанные 7 ходов, причём в 10 из них есть вызовы `formatter_*`; ещё одна — неверный ответ. С выключенными формат-инструментами обрывов нет совсем.
- **Поиск по имени** снимает почти весь оставшийся расход на карте. На большой карте он стоит 9 660 токенов за три попытки вместо 179 994. Вместе с сокрытием формат-инструментов выходит 3 928 токенов на подтверждённый ответ против 104 775 у 3.1.2 — в 27 раз меньше.
- **Исправление типов на этих задачах отдельной экономии не даёт.** stock-quiet почти совпадает с raw-quiet: неоднозначная таблица теперь отдаётся исходным JSON, как и в raw. Исправление защищает тех, у кого включён автоформат: по тексту 3.1.2 два разных входа были неотличимы (это проверяют новые тесты). В замере системная подсказка стенда велит при неоднозначности перечитать результат с `_render: json`, и модель так и делала, так что выигрыш по точности здесь не виден.
- **Разброс между запусками заметный.** Профиль raw на 3.1.2 в первом прогоне дал 13/18, здесь 10/18. Различие в 2–3 ответа из 18 — в пределах шума. Различие 10/18 против 18/18 — нет.
- **Ограничение замера.** Профиль lookup-quiet работает на сохранённых картах через тестовый сервер, который повторяет параметр, описание и текстовый вывод настоящего `map name=`. Сам `any_txt_parser` проверен сквозной цепочкой без модели (раздел 4). Задачи на типы и страницы — искусственные пары с заранее известным ответом.

Сырые данные, стенд и сводка: `outputs/strata-iq4xs-256k-toolfmt-3.1.3/` рядом с планом.

## 4. Проверка

- **Тесты на Linux:** 537 тестов workspace проходят, 0 падают. Добавлены:
  - `tests/renders.rs` — пять воспроизводимых сбоев из `test_toolfmt.py`: массив и строка, объект и строка, `null` и `"null"`, повторяющийся ключ, курсор, упомянутый в тексте;
  - `tests/formatter_tools.rs` — шлюз без формат-инструментов;
  - `map_looks_up_a_file_name_in_the_whole_project` в navguard — одинаковые имена в разных каталогах, регистр, отсутствующий файл, имя с каталогом, исключённый файл, предел `max_files`, совпадение чисел с полной картой, неизменный JSON обычной карты.
- **Дополнительные тесты** `test_toolfmt.py`: на 3.1.2 падали 5 из 12, на 3.1.3 проходят все 12 — и с Linux-бинарником, и с `toolfmt.exe` под Wine.
- **Сквозная цепочка** настоящий `any_txt_parser mcp` → шлюз `toolfmt` с `formatter_tools: false`, без модели:
  - в `tools/list` только `catalog` и `call_tool`;
  - карточка `map` показывает параметр `name` с примером;
  - `name=lib.rs` дал 18 совпадений в разных каталогах;
  - отсутствующее имя — ответ без ошибки, `src/lib.rs` — ошибка, вызов без `name` — прежняя карта.
- **Clippy:** в изменённых строках замечаний нет.

## 5. Сборка

| Файл | Как собран | Проверка |
|---|---|---|
| Linux `toolfmt`, `any_txt_parser` | `cargo build --release --locked`, rustc 1.97.1, x86_64-unknown-linux-gnu | нужен glibc 2.39 (`toolfmt`) и 2.34 (`any_txt_parser`) |
| Windows `toolfmt.exe`, `any_txt_parser.exe` | кросс-сборка на Linux: rustc 1.97.1, цель `x86_64-pc-windows-gnu`, компоновщик mingw-w64 GCC 14 (Debian 13, в одноразовом контейнере), `+crt-static` | импорт только системных DLL (kernel32, ntdll, msvcrt, ws2_32, bcryptprimitives, api-ms-win-core-synch); под Wine: `--version`, 12 дополнительных тестов, `map --name` |

**Отличие от 3.1.2 под Windows.** Выпуск 3.1.2 собран на Windows целью MSVC (`x86_64-pc-windows-msvc`, статический CRT, `/Brepro`). Здесь цель GNU, потому что инструментов MSVC на этой машине нет. Эта сборка зависит от `msvcrt.dll`, которая есть в любой Windows 10/11, а не от VC++ Redistributable. Байты отличаются от сборки MSVC, Rust-тесты под Windows не запускались. Для каноничной MSVC-сборки и полного прогона тестов на Windows распакуйте `source/` и запустите `build_release.bat`.

Контрольные суммы — в `SHA256SUMS.txt` пакета.

## 6. Как включить

```json
{
  "formatter_tools": false,
  "mcpServers": {
    "atp": {"command": "C:/tools/any_txt_parser.exe", "args": ["mcp", "--root", "C:/work/project"], "auto": true}
  }
}
```

Агент находит параметр `name` в карточке `map`: `call_tool tool=map args={"name": "main.rs"}`.

## 7. Что не сделано

- **Выборка записи по номеру (`record_number`), явное поле типа и `cursor_used`.** Они были в прототипе плана. У настоящих источников с устойчивым идентификатором это строки 3–4 таблицы этапа 2, в выпуск не вошли.
- **Явный стандарт `objects_table` по-прежнему показывает вложенный объект строкой с JSON.** Это закреплено старым тестом `toon_quotes_what_would_be_misread`. Исправлен только автоформат, как сказано в плане.
- **`formatter_inspect` с рейтингом методов по объёму ответов** (этап 4 плана) не сделан.
- **Повтор на втором проекте и рабочих запросах** перед сменой значений по умолчанию (этап 3) не проводился. Прогон на Qwen3-VL отменён по вашему решению.
