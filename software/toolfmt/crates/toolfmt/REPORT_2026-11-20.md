# Report: toolfmt 3.1.3 and `map --name`

Date: 2026-11-20. Branch `toolfmt-3.1.3-fixes`, from `b4a4125` (toolfmt 3.1.2). Packages: `dist/toolfmt-3.1.3/` (Windows) and `dist/toolfmt-3.1.3-linux-x86_64/` (Linux).

## 1. Where the changes came from

The toolfmt improvement plan was based on a measurement of version 3.1.2 with Qwen3-VL-30B-A3B in a 64K window. The measurement was repeated with a different model and a larger window: Qwen3.8-Flash-Next UD-IQ4_XS on Strata, 256K. The first run, 72 attempts on 3.1.2, showed three things.

- **The cause of the failures on the large map is not the window.** A map of 1 000 files (57 000 tokens) fits into a 256K window, and accuracy did not grow. The model cannot find the line it needs in a long list and re-reads the map.
- **Almost all the failures were "7 moves with no answer."** The model spent moves on `formatter_inspect` and `formatter_save_standard`, including `dry_run`. There were almost no wrong answers.
- **The bench undercounted correct answers.** It counted an answer only if it was clean JSON. In 11 of the 72 attempts the correct JSON came after an explanation and was counted as an error.

Hence the composition of the release: fix the type and cursor guarantees (stage 1 of the plan), remove the formatter tools from the agent's working set, and add file lookup by name in the real source (stage 2, first line of the table).

## 2. What changed

### toolfmt 3.1.3

1. **The auto-table no longer confuses types.** A nested array `[1,2]` in a cell was printed the same way as the string `"[1,2]"`. An object was printed as a string with the same JSON. Of repeating keys only one was shown. Now the built-in auto-format returns the output unchanged in such cases. An explicit `objects_table` standard on a repeating key falls back to the raw output (`[fallback:raw] objects_table: an item repeats a key`). Code: `table_ambiguity` in `src/render.rs`.
2. **Values in `key: value` lines are distinguishable.** A line that reads as another type (`null`, `true`, `42`, `[...]`, `{...}`, `"..."`) is put in quotes: `total: null` and `total: "null"` no longer match.
3. **Page cursors (I8).** Earlier, the `cursor:` line was not added if the key name and the value happened to appear somewhere in the text, even in different places. Now the renderer reports which fields it printed verbatim (`Effect::shown`): the envelope line, the whole document, the substitution `{result.<path>}` in `expression`. The gateway trusts only this. POST operations reset the confirmation. The line format is unchanged: `cursor: <path>=<value>`.
4. **`"formatter_tools": false`** in `upstreams.json`. The formatter tools do not appear in `tools/list` and not in the instructions; a call to them answers "unknown tool". Standards continue to be applied. The default value is `true`, the behavior is the old one.

### any_txt_parser / navguard

5. **`map --name NAME`** (in MCP — the parameter `name`). Returns only the files whose last path part exactly equals the name, case-sensitively. The search goes through the whole project up to the `max_files` limit; the totals are still over all files. Every match has the full relative path, the line count and a token estimate, binaries a size. The tree is not printed. If there is no such file, this is a normal answer (`no file with this name`); a name with a directory is an error, code 3. In JSON the fields `name` and `matched` appear; a regular map does not have them, and its output is unchanged. The tool's description has the example `{"name": "main.rs"}`.

### What a 3.1.2 user may notice

- In auto-format, output with nested values in a list of objects is no longer turned into a table and arrives as is.
- In envelope lines, values of the form `"null"` or `"42"` are now in quotes.
- The `cursor:` line can appear where it was not there before: the text mentioned a cursor, but the renderer did not print it.
- `any_txt_parser.exe` in the package is built from the same commit and calls itself `1.5.0`, although it contains unreleased changes from the "Unreleased" section of the changelog, including `map --name`. The parser's version number was not changed — the release decision is yours.

## 3. The measurement

The conditions are the same as in the first run on Strata. Model Qwen3.8-Flash-Next UD-IQ4_XS, context 262 144, thinking off. Temperature 0, seed 29, no more than 7 model calls and 300 output tokens per move. Six tasks, five profiles, three series with different ordering — 90 attempts in total. An answer is counted if the last JSON in it matched the reference value and the tool output contained data to justify it. Strict scoring (the whole answer is JSON) is given separately.

**Conclusions.**

- **Hiding the formatter tools** gave the most: 10/18 → 18/18, spend per confirmed answer 7.8× lower. Of the 13 failures in the raw and addressed profiles, 12 were exhausted 7 moves, and in 10 of them there are `formatter_*` calls; one more was a wrong answer. With the formatter tools switched off there are no cut-offs at all.
- **Lookup by name** removes almost all of the remaining spend on the map. On the large map it costs 9 660 tokens for three attempts instead of 179 994. Together with hiding the formatter tools that is 3 928 tokens per confirmed answer against 104 775 on 3.1.2 — 27× less.
- **The type fixes give no separate savings on these tasks.** stock-quiet is almost the same as raw-quiet: the ambiguous table is now returned as the original JSON, as in raw. The fix protects those who have auto-format enabled: in the 3.1.2 text two different inputs were indistinguishable (the new tests check this). In the measurement the bench's system prompt tells the model to re-read the result with `_render: json` in case of ambiguity, and the model did exactly that, so the accuracy gain is not visible here.
- **The spread between runs is noticeable.** The raw profile on 3.1.2 gave 13/18 in the first run; here it is 10/18. A difference of 2–3 answers out of 18 is within the noise. The difference of 10/18 against 18/18 is not.
- **Limit of the measurement.** The lookup-quiet profile works on saved maps through a test server that repeats the parameter, the description, and the text output of the real `map name=`. `any_txt_parser` itself was checked by an end-to-end chain without a model (section 4). The type and page tasks are artificial pairs with a known answer in advance.

Raw data, the bench, and the summary: `outputs/strata-iq4xs-256k-toolfmt-3.1.3/` next to the plan.

## 5. Build

| File | How built | Check |
|---|---|---|
| Linux `toolfmt`, `any_txt_parser` | `cargo build --release --locked`, rustc 1.97.1, x86_64-unknown-linux-gnu | needs glibc 2.39 (`toolfmt`) and 2.34 (`any_txt_parser`) |
| Windows `toolfmt.exe`, `any_txt_parser.exe` | cross-build on Linux: rustc 1.97.1, target `x86_64-pc-windows-gnu`, linker mingw-w64 GCC 14 (Debian 13, in a throwaway container), `+crt-static` | imports only system DLLs (kernel32, ntdll, msvcrt, ws2_32, bcryptprimitives, api-ms-win-core-synch); under Wine: `--version`, the 12 extra tests, `map --name` |

**Difference from 3.1.2 on Windows.** The 3.1.2 release was built on Windows with the MSVC target (`x86_64-pc-windows-msvc`, static CRT, `/Brepro`). Here the target is GNU, because there are no MSVC tools on this machine. This build depends on `msvcrt.dll`, which is present in every Windows 10/11, not on the VC++ Redistributable. The bytes differ from the MSVC build, and the Rust tests were not run on Windows. For the canonical MSVC build and a full test run on Windows, unpack `source/` and run `build_release.bat`.

Checksums — in the package's `SHA256SUMS.txt`.

## 6. How to enable

```json
{
  "formatter_tools": false,
  "mcpServers": {
    "atp": {"command": "C:/tools/any_txt_parser.exe", "args": ["mcp", "--root", "C:/work/project"], "auto": true}
  }
}
```

The agent finds the `name` parameter in the `map` card: `call_tool tool=map args={"name": "main.rs"}`.

## 7. What was not done

- **Selection of a record by number (`record_number`), an explicit type field, and `cursor_used`.** They were in the plan's prototype. With real sources having a stable identifier these are lines 3–4 of the stage-2 table; they did not make it into the release.
- **An explicit `objects_table` standard still shows a nested object as a JSON string.** That is fixed by the old test `toon_quotes_what_would_be_misread`. Only the auto-format was fixed, as stated in the plan.
- **`formatter_inspect` with method ratings by response size** (stage 4 of the plan) was not done.
- **The repeat on a second project and real queries** before changing the defaults (stage 3) was not carried out. The run on Qwen3-VL was cancelled by your decision.
