# Part I — Product overview

## 1. What is Cube v5?

Cube v5 is a single, self-contained Windows x64 executable that speaks the Model Context Protocol (MCP) over stdio. An MCP `tools/list` request exposes **87 tools** for:

- exact integer and decimal-style operations (address reads against the precomputed table — section 2);
- complex-form operations on integer (re, im) pairs;
- integer diagnostics and structural analysis;
- OPTG path and address-stack decomposition (OPTG: the engine's path/structure naming — reference section 9.5);
- spatial placement, movement, floor, and distance operations;
- E8 root-system operations, bridge/address mapping, batch projection, statistics, and table matrix multiplication;
- exact integer vector algebra;
- verification and symbolic operations;
- utilities (deterministic pseudo-random generation, runtime reset, canonical help).

The program runs locally on Windows 10/11 x64. It requires no GPU, no Python installation, and no network access. On first start the executable generates its runtime lookup table (`cube_v5.bin`, about 272 MB, about 13 seconds on a reference host) next to itself; warm starts complete in well under a second. Results are read from this precomputed, verified local table — the runtime performs no arithmetic and exposes no data files other than the table.

`cube_v5.bin` is a runtime artifact generated by the executable on first start; it is not distributed and must not be added to a Git repository.

> **Scope note.** Cube v5 implements the experimental "Opterium" framework (the engine's geometric address framework), which is not established peer-reviewed mathematics. Treat framework-specific outputs as experimental; they are not independent mathematical proofs.

## 2. Conceptual model

Cube is not conventional mathematical software. It has its own geometric and addressing semantics. This section is the operational reference for all users — especially AI agents — of the tools in the [Complete Technical Reference](CUBE_REFERENCE.md).

**Address-read execution model.** Per the canonical `help` reference, operation results pre-exist in a precomputed verified lookup table: the runtime performs no arithmetic; each call resolves to an address in that table. In the engine's own model a "wrong answer" is impossible — only an instruction pointing to a different address than intended is possible. The matching practice is to **audit addresses (witnesses), not values**: use `cubint_witness` and the other witness/reporting tools to check which address was resolved.

**Cube-native values.** Cube-native complex-form values must not be interpreted automatically as conventional complex numbers. Expressions such as `(1+2i)` and `(3+4i)` can represent spatial addresses in Cube's model. The `cubcomplex_*` family is documented by Cube's own reference **without a conventional complex-algebra interpretation** (for `mul` the canonical help states `exact; orientation adds mod 4, no float angles`; for `pow` it gives the verified witness `cubcomplex_pow(1,1,100) -> -1125899906842624 (=2^50*(-1))`). Treat returned values as Cube-native results: use them as returned, without re-deriving them in external algebra.

**No imposed identities.** Do not impose conventional algebraic identities on Cube operations unless the specific public tool contract establishes them (for example, `cubint_add` documents that `a + b - b == a` holds by design). Geometric, address, and diagnostic outputs follow Cube's own model. An unusual diagnostic verdict (`REJECTED`, `QUARANTINE`, `UNCERTAIN`) is a classification produced by the diagnostic system on the given inputs — it is not evidence that an underlying operation failed or that the engine is defective.

**The engine owns its geometry.** Cube's addressing, coordinate handling, geometry, and bounds behavior are owned by the engine. Users supply arguments in the format the exposed API requires. No public coordinate limits exist beyond the restrictions documented in the API (for example, the E8 root index range `0..239` of the `e8_*` root tools). The internal Cube dimensions and coordinate-space extents are not part of the public contract and must not be inferred, documented, or used to restrict inputs.

## 4. Is Cube right for your task?

**Cube is useful for:**

- **Local AI-agent computation.** A deterministic, self-contained MCP tool server that an agent can start on demand and call with exact, reproducible results.
- **Exact integer and decimal-style operations.** Integer and decimal-style operations that return exact, precomputed results at tested sizes, with no IEEE rounding (`0.1 + 0.2 = 0.3` exactly).
- **E8-related work.** Root lookup and geometry, partner/aligned shells, distances, batch projection of many values, statistics, and table-based matrix multiplication.
- **Geometric and address-oriented workflows.** OPTG paths, address stacks, 26-neighborhoods, spatial placement/movement with floor semantics, and E8 address round-trips.
- **Vector processing.** Exact integer vector pipelines: arithmetic, statistics (scaled integers), norms, normalization, clipping, sorting, deduplication.
- **Diagnostic and verification workflows.** Factorization, divisor structure, 14-channel pair/group comparison, closure verification, and symbolic invariants over integer structure.

**Considerations before adopting:**

- **Platform.** Windows 10/11 x64 only. The distribution is binary-only: `cube.exe` plus this README; no source code is provided or implied.
- **Local runtime table.** First start generates `cube_v5.bin` next to the executable (~272 MB; first start ≈13 s on a reference host — section 5); budget about 300 MB of free disk space.
- **Synchronous MCP calls.** One call is processed at a time per connection; a blocked call (for example, a large diagnostic input) stalls that session and requires a session restart ([CUBE_REFERENCE.md, section 12](CUBE_REFERENCE.md#12-errors-and-troubleshooting)).
- **Known tool-specific limitations.** Large-operand diagnostics can block; `vec_dot` rejects negative element products; `cubint_pow` has documented anomalies at large and negative exponents ([CUBE_REFERENCE.md, section 14](CUBE_REFERENCE.md#14-limitations-and-important-behavioral-characteristics)).
- **Cube-native semantics.** Geometric and complex-form outputs follow Cube's own model; do not judge them by conventional algebra (section 2).

The reader can make an informed go/no-go decision from this overview alone; the [Complete Technical Reference](CUBE_REFERENCE.md) is the complete operational reference for those who adopt it.

## 5. Architecture and requirements

**Runtime model.**

- `cube.exe` is a single Windows x64 binary (6,612,992 bytes in the published build) with no external runtime dependencies; a clean directory containing only `cube.exe` runs the full server.
- The executable is a self-contained bundle that runs as a two-process pair: the first process spawns a second, and both report the same executable path. When stopping the server, terminate the whole process tree (for example `taskkill /T /F /PID <pid>` on Windows), not just the first process.
- MCP communication is newline-delimited JSON-RPC 2.0 over stdio: requests on stdin, responses on stdout, diagnostics on stderr. Supported methods: `initialize`, `notifications/initialized`, `tools/list`, `tools/call {name, arguments}`. Unknown methods return JSON-RPC error `-32601`. The server is synchronous.
- Execution model: operations are address reads in the precomputed verified table (section 2). The table is generated once (first start or `--generate`) and, when a `cube.sha256` file is present next to it, is hash-verified at startup; without it the hash check is skipped.

**Runtime files.**

| File | Location | Managed by |
|---|---|---|
| `cube.exe` | user-chosen folder | user (distributed) |
| `README.md` | beside `cube.exe` | user (distributed) |
| `CUBE_REFERENCE.md` | beside `cube.exe` | user (distributed) |
| `cube_v5.bin` | next to `cube.exe` | **generated automatically** on first start (measured 272,000,016 bytes); not distributed; never commit to Git |
| `cube.sha256` (optional) | next to `cube_v5.bin` | user-provided file containing the SHA-256 hex digest of `cube_v5.bin`; if present, the server verifies the table hash at startup and refuses to run on mismatch |
| `mcp_debug.log` | system temp directory | generated; inspect for errors such as `Bad magic` |
| 240×240 E8 product table | in memory | generated by `e8_table_build`; cached across calls within a session; no on-disk cache file is created |

**Requirements.**

- Windows 10/11, x64.
- An MCP-capable client: Claude Desktop, LM Studio, Cursor, opencode, or any JSON-RPC 2.0 stdio client.
- About 300 MB of free disk space for the generated table.
- No GPU; no network access; no Python installation (Python is only needed if you wish to run your own independent reference checks beside Cube).

Installation, CLI, and protocol details are given in full in the [Complete Technical Reference](CUBE_REFERENCE.md) (sections 6 and 7).
